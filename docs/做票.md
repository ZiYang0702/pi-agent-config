# 做票

开工先派子 Agent 摸底，带回「改哪些文件、哪几处、为什么」，主会话不整份读源码。

## 写票

票上进度只由主会话写，子 Agent 交回的先核实再写。每做完一个阶段（摸底、测试通过、审查完），先提交 git，将交接引用的提交、文档和证据上传到接续者可访问的位置，再逐个验证链接，最后在票下评论。Git 提交 push 到远端分支即可，文档链接指向固定提交及相关章节。

票就是交接文件。评论是结构化总览：只读评论，就能判断当前状态、关键结论、阻塞和下一步；详情通过 pointer 按需读取。评论写八项，没有的写「无」：
1. 做完了什么，一句话。
2. 验证证据：命令和返回的原文。
3. 下一步，谁来做。
4. 定了什么、为什么；用户中途的指令记原话。
5. 否掉的方案和原因，技术方案也算。
6. 报错原文放代码块；关键数字写清是什么、在哪测的。
7. 阻塞点：原因与恢复条件；确需用户决定时，写明具体问题，没有则写「无」。
8. 改了的文件：路径加提交号。

PR、提交、文档里已有的详情只放链接；每个 pointer 写明材料内容、何时需要读取及相关位置。Session 历史仅作补充追溯，链接前确认接续者可访问；关键决定、用户指令和未完成事项提炼到交接中。

上传或链接验证受阻时，先在评论内写足接续所需的信息，注明尚未上传或无法访问的材料、原因与补齐责任人。阶段交接以评论更新成功、全部引用可访问为完成条件；受阻的交接标明待补齐。

## 持续推进与交付

阶段交接更新成功后，继续执行当前授权范围内的下一步。一项工作受阻时，先完成其他可继续的工作。仅在剩余工作确需用户提供信息、决定或授权，或遇到当前无法解除的外部阻塞时暂停；在交接中写清原因和恢复条件，待用户决定的问题必须对应实际阻塞。

实施代码票的默认交付流程：完成修改 → 测试和审查 → 上传分支 → 创建 PR → 检查 CI 结果。与本次改动有关的 CI 失败继续定位修复。已有本次任务的合并授权时，检查通过后继续合并；没有合并授权时，报告 PR 可合并。最终回复分别说明修改完成情况、PR 链接、CI 结果和是否已合并。用户明确限定任务范围时，按用户要求执行。

## 交接

关键阶段完成时按上面的八项写交接；阻塞或下一步变化时，更新当前阶段的同一条交接，并更新其中的时间。同一阶段的当前进度以这条交接为准，证据明细通过链接查阅。

手动 compact 前，先更新当前交接，写明任务票位置和下一步。自动 compact 依靠工作中已维护的交接恢复。

compact 后恢复时，从保留上下文定位当前任务票，按交接更新时间找到最新交接，确认下一步后继续。需要细节时，只读取证据链接中的相关片段；当前任务票无法确定时，先向用户确认。
